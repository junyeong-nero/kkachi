# 입력 버스

기기에서 들어온 입력을 core 가 받아 처리하고, 출력을 어디로 보낼지 정하는 방식. 구조 전체는 [modules.md](modules.md), 기기 기능은 [sensors.md](sensors.md), 화면 동작은 [design.md](design.md).

## 모델

입력은 사건이고 출력은 명령이다. 두 흐름은 서로를 모른다.

```
입력 기기 ──(사건)──▶ kkachi-devices ──▶ core 버스: 접수 → 까치 홈 대화의 한 턴 → 들은 기기로 답
                                                                            │
출력 기기, 까치 홈 ◀──(명령)───────────────────────────────────────────────────┘
```

- 기기는 사건을 내보내고 끝낸다. 답을 기다리지 않는다. 답은 들은 기기로 따로 온다(`device_reply`)
- ACK 는 전송 확인이다. "core 가 사건을 받았다"는 뜻이고, 결과와는 상관이 없다
- 출력은 core 가 정한 대상에게 단방향으로 간다. 말하기처럼 완료를 알려주는 출력도 다시 보내지는 않는다. 같은 말을 두 번 하는 것보다 한 번 놓치는 쪽이 낫다

에이전트가 부르는 당겨오는 입력(사진, 소리 크기, 센서)은 지금처럼 요청과 응답을 id 로 짝 맞춘다. 이 문서는 기기가 먼저 시작하는 밀려오는 입력을 다룬다. 지금은 말 걸기 하나이고, 나중에 움직임 감지와 호출어가 같은 길로 들어온다.

## 전송

```
기기                        kkachi-devices                       core
input {id, kind, at, 오디오} ─▶ 토큰·스위치 확인, id 중복 제거 ─▶ POST /api/bus/input
ack {id, ok}               ◀─────────────────────────────────── 접수 (만료면 거절)
                                                               받아쓰기 → 까치 홈 대화의 턴
reply {inputId, heard, 답}  ◀── device_reply (core 전용 도구) ◀── 한 문장씩
```

- id 는 기기가 만든다(UUID). devices 서비스와 core 가 둘 다 최근 id 를 기억해서, 같은 사건은 한 번만 처리한다
- 기기는 ACK 를 받을 때까지 사건을 대기열에 두고, 5초마다 그리고 다시 연결될 때 같은 id 로 다시 보낸다
- 유효시간은 말한 시각(`at`)에서 60초다. 그보다 늦게 도착한 사건은 버린다. 10분 늦게 도착한 "불 꺼줘"가 그때 실행되면 안 된다
- ACK 는 core 가 접수했을 때 보낸다. core 가 꺼져 있으면 ACK 가 없고, 기기가 유효시간 안에서 계속 다시 보낸다. 대기열은 기기에만 있고 devices 서비스는 상태를 갖지 않는다
- 답은 `reply` 로 들은 말과 답(글, 음성)이 함께 온다. 답은 다 쓴 뒤에 한 번에 오지 않고, 에이전트가 문장을 끝낼 때마다 한 문장씩 온다(`part` 0, 1, … 그리고 `last`). 문장마다 목소리를 따로, 나란히 만들기 때문에 기기는 번호 순서로 말한다. 도구를 부르기 전에 한 말("찾아볼게요")도 말해서 기다리는 동안 조용하지 않게 하고, 끝나면 화면에는 답만 남긴다. 서버 목소리(Edge TTS)가 한 문장에 6초 넘게 걸리면 그 문장은 기기 목소리로 말한다. 전에는 답 전체를 기다렸다가 전체를 한 번에 소리로 만들어서 10~30초가 걸렸다. 기기가 잠깐 끊겼다 돌아오면 2분 안의 답은 다시 보낸다

## 정해진 방식

예전에는 까치 홈 설정에서 대화 세션, 답하는 곳, 개인적인 내용, 도구, 내 MCP, 새 대화 시간을 고를 수 있었다. 혼자 쓰는 집이라는 가정으로 하나로 정하고 설정을 뺐다.

- 기기에서 한 말은 까치 홈 대화의 한 턴이 된다. 세션은 하나다. 앱을 다시 열거나 지난 대화를 열어도 기기 턴이 그 안에 "거실에서"처럼 출처를 달고 있다
- 답은 들은 기기가 소리로 한다. 까치 홈에도 같은 턴이 보이지만 소리로 읽지는 않는다
- 도구는 까치 홈과 같다. `kkachi.mcp.json` 의 도구도, 까치 홈 설정의 도구에서 붙인 MCP 서버도 쓴다. 기기에 말하는 누구나 명령을 실행시킬 수 있다는 뜻이다. 손님이 오는 곳이면 그 기기의 음성을 까치에게서 닫는다
- 개인적인 내용도 가리지 않고 소리로 말한다. 턴 앞에는 `[기기: 거실]` 만 붙는다

## 세션과 커밋

- 까치 홈 턴은 지금처럼 새 메시지가 앞 턴을 멈춘다. 기기 턴은 멈추지 않고 차례를 기다린다
- 기기 턴은 까치 홈 턴과 같은 줄에 서고, 끝나면 core 가 턴 하나를 커밋 하나로 만든다. 같은 레포를 동시에 고치지 않기 위해서다
- 모든 기기 턴은 30분 대화 정리에 `[거실] …`로 들어간다

## 까치에게 열린 것

까치가 기기에서 무엇을 쓸지는 기기마다 하나씩 정한다. 까치 홈의 메뉴에서 기기를 눌러 연다. 기기 화면에는 스위치가 없다. kkachi-devices 가 기기마다 갖고(`data/devices.json`, `POST /api/device/<id>/agent {cap, open}`), 새 기기는 모두 열려 있다.

- 음성: 열려 있으면 기기 화면 가운데에 누르고 말하는 패드가 나오고, 한 말이 까치의 한 턴이 된다. 닫으면 패드가 사라지고, 그래도 들어온 말은 devices 가 거절한다(`switched off`)
- 스피커, 조명, 카메라, 소리 크기, 움직임 센서, 위치: 까치가 도구로 쓴다. 닫힌 것을 쓰려 하면 devices 가 거절하고, `list_devices` 에도 닫혀 있다고 나온다
- 조명은 태블릿만 된다. 조명이 켜지면 화면 전체를 덮어서, 휴대폰에서는 말하는 패드의 터치를 가렸다

기기끼리 에이전트 없이 잇는 길(한 기기의 버튼이나 다이얼로 다른 기기의 조명을 켜기, 무전기처럼 녹음을 다른 기기 스피커로 보내기)은 있었지만 뺐다. 까치는 집에 늘 켜져 있는 에이전트를 어디서든 불러 집을 보고 움직이는 것이 핵심이고, 에이전트 없이 기기끼리 잇는 일은 Home Assistant 나 기기 회사의 앱이 더 잘한다.

## 까치 홈 피드

까치 홈은 열려 있는 동안 `/api/feed` 를 듣는다. 모든 기기 턴과 `send_to_phone` 메시지가 온다. 마지막으로 본 번호를 기억해 두었다가 다시 열 때 그 뒤의 것만 받는다. 피드는 서버 메모리에 최근 100개만 두고, 서버가 재시작하면 비워진다. 기기 턴은 그 기기가 이미 말했으니 폰에서는 소리로 읽지 않는다.
